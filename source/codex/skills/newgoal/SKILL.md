---
# base_project:managed
name: newgoal
description: Research and write a detailed executable plan in GOALS.md. This is planning-only and must never implement the plan. Use for $newgoal or an explicit request to create a base_project goal.
---

Produce `GOALS.md` at the project root as the researched input for `$execgoals`.

**Hard boundary: never execute.** This skill may write only `GOALS.md`, or the standalone document allowed for a pure research goal. It never scaffolds, installs, builds, edits implementation files, or executes an existing plan—even if the request sounds fully approved. Execution requires `$execgoals` or a separate explicit request.

1. Reuse context already established. Ask one brief round only for missing stack, project kind, or greenfield/existing state.
2. Read `~/.codex/base_project/references/project-standards.md`.
3. Classify the request and read the matching file under `~/.codex/base_project/references/goal-types/`:
   - `research.md` for a standalone report or investigation;
   - `fix.md` for reproducible broken behavior;
   - `feature.md` for a bounded addition to a working system;
   - `process.md` for governance, CI, distribution, legal, or other non-product-code work;
   - `build.md` for a full greenfield system.
4. Research current facts and concrete technical choices deeply enough that execution does not need to redo the discovery. Browse when facts may have changed or authoritative sources matter.
5. If `$repertoire` was requested together, finish its domain research first and use `REPERTOIRE.md` as input. If `$council` was also requested, use it only for genuinely contested decisions and honor its separate token-cost confirmation.
5a. Ground every reference before writing it. Open each file the plan will edit and copy its anchors from what is actually there; search for every function, flag, path, command, and test name the plan mentions and correct or drop any that does not exist. Record the commit the plan was grounded against (`git rev-parse --short HEAD`) in the section's first paragraph. Facts about the outside world (versions, APIs, defaults) come from a source read in this pass and cited per item; when no source was read, the item says so instead of stating the fact from memory.
6. Write the plan in English as ordered, checkable items grouped by the selected goal type's areas. Tag manual work explicitly and define “Done when” evidence. Put a small Mermaid dependency flowchart under each `GOALS N` heading.
6a. Write every item to the executable item contract. The executor may be a weaker model with none of this research in its context; every judgment call left inside an item becomes a guess there. Put the line `<!-- item-contract: v1 -->` under each new `GOALS N` section's stage map so the structure validator checks the fields, and give every item these sub-bullets, in this order: `Files:` every path the item creates or edits, each marked `(new)` or `(exists)`; an `(exists)` path was opened during this planning pass, not assumed. `Anchor:` for an edit to an existing file, a line or unique heading copied verbatim from that file during this pass, so the executor finds the location instead of inferring it. `Change:` the exact text to add or replace when it is about 15 lines or fewer; otherwise a precise specification — names, signatures, inputs, outputs, error cases. Never "improve", "clean up", "update as needed", or "handle appropriately". `Do not touch:` adjacent files or behavior that must stay as they are, whenever a plausible over-edit exists. `Verify:` the exact command or check and its expected result (exit code, test name, match count), so "done" is observed, not judged. `Source:` the URL and access date for every external fact the item relies on (version, API, flag, default). A fact not confirmed in this pass is written `(unverified — confirm before executing)`, which makes the item a stop point for `$execgoals`, never a silent assumption. A `manual` item needs only `Verify:` (the evidence the user provides). One item is one coherent change that one `Verify:` can prove: split an item that edits more than three files or still contains a choice. Every choice is settled in the plan — a `Decisions` subsection stating the option taken and why — or becomes its own `manual` item; an item handed to `coder` contains no open decision. Long text that several items reuse goes once in a `Canonical texts` subsection, and items reference it by name.
6b. Open each `GOALS N` section with a stage map. Group the section's items into stages and show them as a table — `Stage | Items | Depends on | Can run in parallel with` — and draw step 5's Mermaid flowchart at that same stage level. Two stages are parallel only when neither needs the other's result and they edit no file in common; otherwise they are sequential. Name each stage after what it delivers, and use the same names when explaining the plan to the user. `$execgoals` still runs items in written order; the parallel column tells the user which stages can go to separate sessions.
6c. Write item text in controlled English, modeled on ASD-STE100 Simplified Technical English. The executor follows words literally, so write each item like a maintenance procedure: Write one instruction per sentence, as a command: "Replace X with Y.", not "X should probably be updated to Y". Keep an instruction to 20 words or fewer and a descriptive sentence to 25 words or fewer. A longer sentence usually holds two ideas: split it. Use the active voice. Do not use "-ing" verb forms as instructions. Use one word for one meaning. After you name a thing (a file, a block, a stage), use the same name every time; do not use synonyms. Keep the articles ("the", "a"); do not compress sentences into fragments. Write a limit or a warning as a command, before the step it applies to. Do not use vague words: "appropriate", "properly", "as needed", "etc.", "and so on". Code, paths, commands, and quoted anchors are exempt: copy them exactly. This rule applies to the checklist items; the rationale sections of a plan stay in normal English.
7. If `GOALS.md` exists, read the active root file and merge; never overwrite prior plans silently. If `dev/goals-archive/README.md` exists, read its index too and open individual archived plans only when historic scope/evidence is relevant. Use unique section and item identifiers.
8. For a purely research-only goal with no later implementation, follow `research.md` and write the standalone deliverable instead of ceremonial `GOALS.md` checkboxes.
9. Report the path and, in the user's language, the stage map: each stage in order, what it delivers, and which stages can run at the same time. Then ask whether the user wants to proceed with `$execgoals` or adjust the plan first. Do not begin implementation.
